# B4 — الربط غير القابل للتغيير مع هوية Supabase Auth

**الحالة التقنية:** مكتمل ومثبت محلياً  
**بوابة B4 الأصلية:** `REVIEW_REQUIRED`  
**البوابة النهائية بعد مراجعة B4.1:** `PASS`  
**الفرع:** `develop`  
**الهجرة:** `0004_immutable_auth_identity`  
**بصمة ما بعد B4:** `0cc36df95708af1261001284404a9262e6e05717060090a1714d682e7dfb0a79`

سبب المراجعة التشغيلية الأصلية موضح في القسم 21: حدثت محاولة اتصال غير مقصودة بوجهة `.env` المستضافة أثناء التحقق، لكنها فشلت في حل المستأجر/المضيف قبل تنفيذ أول عبارة SQL. لم تُعدّل قاعدة مستضافة أو إنتاجية. أغلق B4.1 السبب وأثبت المنع قبل إنشاء الاتصال؛ انظر القسم الأخير.

## 1. الملخص التنفيذي

استبدلت B4 الاعتماد التشغيلي على البريد الإلكتروني بمعرّف Supabase Auth الثابت `auth.users.id`. أصبح لكل سجل داخلي في `public.users` رابط اختياري وفريد `auth_user_id UUID`، ويبحث محلل الهوية المركزي بهذا UUID أولاً ودائماً. يظل البريد بيانات ملف شخصي/اتصال، ولا يؤثر تغييره بعد الربط في المستخدم الداخلي أو العضوية أو مساحة العمل.

تدعم الهجرة قواعد البيانات الجديدة والحالية: تربط فقط التطابقات القديمة الوحيدة والمؤكدة، وتترك الحالات غير المطابقة أو الملتبسة بلا ربط، وترفض التعارض. لا تحذف أو تدمج مستخدمين، ولا تنشئ مساحة عمل أثناء الهجرة. غُيّر مساعد RLS الأدنى اللازم ليعتمد UUID بدلاً من البريد، مع إبقاء خصائص `SECURITY DEFINER` و`search_path` والصلاحيات المقيدة.

## 2. خطر الهوية السابق

كان `resolveAuthorizedWorkspace` يبحث عن `public.users.email` باستخدام بريد جلسة Supabase. تغيير بريد Auth كان قد يمنع العثور على السجل القديم، ثم ينشئ مستخدماً داخلياً ومساحة عمل جديدين. كذلك كان `current_workspace_ids()` يربط `auth.users` و`public.users` بالبريد، ولذلك كانت عضوية المستأجر تعتمد على معلومة قابلة للتغيير.

## 3. تدقيق مسارات حل الهوية

| المسار | السلوك قبل B4 | السلوك بعد B4 |
|---|---|---|
| التسجيل | إنشاء Supabase Auth فقط؛ لا مستخدم داخلي فوراً | دون تغيير؛ الربط/الإنشاء عند أول دخول مصرح |
| تسجيل الدخول | Supabase Auth ثم bootstrap بالبريد | Supabase Auth ثم `auth_user_id` |
| OAuth | لا يوجد مسار OAuth تطبيقي مستقل حالياً | لا تغيير |
| استعادة الجلسة | `supabase.auth.getUser()` | يمر UUID والبريد وحالة التحقق للمحلل المركزي |
| Middleware | إثبات جلسة Supabase؛ لا ينشئ مستخدماً داخلياً | لا تغيير |
| `/auth/confirm` | تأكيد OTP/جلسة؛ لا ربط داخلي مباشر | لا تغيير |
| أول دخول/Workspace bootstrap | العثور/الإنشاء بالبريد | UUID أولاً؛ ربط قديم مضبوط أو إنشاء مشروع جديد ذرياً |
| طلبات الخادم والصفحات المحمية | `getAuthorizedWorkspace()` | نفس المدخل المركزي، لكن بهوية UUID ثابتة |
| دعوة عضو | العثور أو إنشاء مستخدم بالبريد | البريد للاتصال فقط؛ placeholder بلا UUID، مع كشف تصادم الهوية المرتبطة |
| تحديث الملف/البريد | البريد قابل للتعديل | يبقى قابلاً للتعديل؛ لا يغيّر `auth_user_id` |
| RLS | عضوية `current_workspace_ids()` عبر مساواة البريد | عضوية عبر `users.auth_user_id = auth.uid()` |

لا توجد عمليات أخرى مكتشفة تنشئ المستخدم الداخلي الممثل للجلسة. الخدمات الأخرى تعتمد `userId` أو `teamMemberId` أو `workspaceId` بعد حل الطلب.

## 4. نموذج البيانات الحالي

- المفتاح الأساسي لـ `public.users` هو UUID داخلي مستقل.
- `users.email` غير فارغ وفريد وفق مساواة PostgreSQL الحالية الحساسة لحالة الأحرف؛ تدفق التطبيق يطبع البريد إلى lowercase، لكن البيانات القديمة قد تحتوي اختلاف casing.
- الحقول الاختيارية تشمل الاسم والصورة والهاتف، مع حذف ناعم وحالة تحقق بريد.
- المراجع المباشرة للمستخدم تشمل مالك Workspace، و`team_members.user_id`، ومستخدم محادثة AI، ورافع الملف، ومستلم الإشعار، ومنشئ نسخة الموقع، وممثل نشاط CRM، والمكلّف بفرصة CRM.
- مراجع الفوترة/الحجز التشغيلية الحساسة تعتمد غالباً `team_members.id`، وقد حصّنتها B3.2 بعلاقة Workspace مركبة.
- كانت دلالة الجلسة الوحيدة المعتمدة على البريد في bootstrap ومساعد RLS؛ الدعوة تستخدم البريد كعنوان اتصال/مطابقة placeholder وليست إثبات جلسة.

## 5. عقد الهوية المعتمد

العقد هو:

`auth.users.id UUID → public.users.auth_user_id UUID → Verix user UUID`

الرابط اختياري للمستخدمين القدامى أو المدعوين الذين لم يسجلوا الدخول، وفريد عند وجوده، ولا يتغير أو يُمسح بعد ضبطه. لا تعني مساواة البريد دمج حسابين، ولا يُستخدم البريد للعثور المعتاد على هوية مرتبطة.

## 6. تصميم الهجرة

أضيفت الهجرة `0004_immutable_auth_identity.sql` بعد `0003`. ترتيبها:

1. إضافة `users.auth_user_id UUID` nullable.
2. إضافة القيد الفريد `users_auth_user_id_uq`؛ وهو ينشئ الفهرس المطلوب ويسمح بعدة قيم NULL.
3. إثبات وجود `auth.users.email_confirmed_at`.
4. تشغيل تصنيف preflight تجميعي ورفض `CONFLICT`.
5. ربط التطابقات الدقيقة المؤكدة فقط.
6. إنشاء trigger عدم قابلية التغيير وسحب تنفيذ دالته من الأدوار العامة/التطبيقية.
7. استبدال جسم `current_workspace_ids()` بربط UUID.

لم يُضف FK عبر schema إلى `auth.users`. هذا قرار مقصود ومتوافق مع ADR: يجب أن يبقى السجل الداخلي وآثاره التاريخية عند حذف هوية Auth، كما أن FK يربط دورة حياة التطبيق ببنية Supabase الداخلية. العلاقة مفهومية ومثبتة عند الربط، والفريد يمنع ربط UUID بأكثر من مستخدم.

## 7. فحص الربط القديم

أداة الفحص `test:db:identity:preflight` للقراءة فقط ولا تعرض بريداً أو UUID. تصنّف:

- `EXACT_MATCH`: سجل داخلي واحد وهوية Auth مؤكدة واحدة للبريد المطبع.
- `NO_AUTH_MATCH`: لا توجد هوية Auth مؤكدة.
- `AMBIGUOUS_MATCH`: أكثر من سجل داخلي أو أكثر من Auth للبريد.
- `ALREADY_LINKED`: UUID موجود وله هوية Auth فعلية.
- `CONFLICT`: UUID مخزن بلا هوية إثبات أو حالة غير آمنة.

توقف الهجرة عند `CONFLICT`. تترك `NO_AUTH_MATCH` و`AMBIGUOUS_MATCH` بقيمة NULL من دون حذف أو دمج أو provisioning.

## 8. قواعد المطابقة

تُقبل مطابقة البريد فقط كدليل انتقالي لمرة واحدة، وتستخدم `lower(btrim(email))` بما يتفق مع تدفقات التطبيق الحالية. يلزم بريد Auth غير فارغ ومؤكد، وسجل داخلي حي واحد، وهوية Auth مؤكدة واحدة. لا يُعدّل `auth.users` ولا بريد السجل الداخلي. بعد الربط لا تُستخدم مطابقة البريد حتى لو صار البريد مساوياً لبريد حساب داخلي آخر.

## 9. محلل الهوية التشغيلي

`resolveInternalIdentityInTransaction` هو المحلل المركزي. يتحقق من UUID، ويأخذ advisory transaction locks للـUUID والبريد المطبع عند توفره، ثم:

1. يعيد السجل المرتبط بالـUUID بصرف النظر عن البريد.
2. يرفض السجل المرتبط المحذوف ناعماً.
3. إن لم يوجد رابط، يرفض البريد الفارغ.
4. يفحص المرشحين القدامى فقط في هذا الفرع الانتقالي.
5. يربط المرشح الوحيد المؤكد، أو ينشئ مستخدماً جديداً مشروعاً، أو يرفض الالتباس/التعارض.

تنفذ هوية المستخدم وتهيئة أول Workspace داخل transaction واحدة. يمنع القفل والقيد الفريد تكرار أول دخول متزامن.

## 10. تهيئة المستخدم الجديد

إذا لم توجد هوية UUID مرتبطة ولا مرشح قديم ولا تعارض، ينشئ المحلل مستخدماً داخلياً واحداً مرتبطاً مباشرة بالـUUID، ثم ينشئ Workspace واحدة وعضوية owner واحدة وفق السلوك السابق. الاختبار المحلي أثبت عدم التكرار وإرجاع `NEW_IDENTITY_PROVISIONED`.

## 11. ربط المستخدم القديم

إذا وجد سجل قديم وحيد ببريد مطابق مؤكّد، يضبط المحلل `auth_user_id` مرة واحدة و`email_verified = true`. إذا كان للمستخدم Workspace أو عضوية قائمة، يعيدها ولا ينشئ Workspace. أثبت اختبار upgrade أن البريد وحقل الاسم والسجلات الأربعة التمثيلية بقيت بلا فقد.

## 12. معالجة التعارض

الأخطاء المضبوطة هي: UUID غير صالح، بريد مفقود، تطابق قديم غير مؤكد، تطابق ملتبس، تصادم رابط، أو مستخدم مرتبط محذوف. في الحالات الملتبسة والمتعارضة لا يحدث merge ولا إنشاء مستخدم أو Workspace. يحول القيد الفريد سباق الربط إلى رفض مضبوط.

## 13. سلوك تغيير البريد

أثبت اختبار التكامل التسلسل المطلوب: إنشاء Auth A وربطه بـVerix A وWorkspace A، ثم تغيير بريد `auth.users` مع ثبات UUID، ثم الحل ثانية. كانت النتيجة نفس `userId` ونفس `workspaceId` ونفس العضوية، مع مستخدم واحد وWorkspace واحدة وعضوية واحدة. كما أثبت اختبار منفصل أن مساواة البريد الجديد لبريد سجل داخلي آخر لا تغيّر الرابط ولا تربط السجل الآخر.

## 14. فرض عدم قابلية التغيير

- لا تعرض خدمات التطبيق أي helper لتغيير `auth_user_id`.
- trigger `enforce_auth_user_id_immutability_trg` يمنع تغيير أو مسح أي قيمة non-null (`23514`).
- محاولة authenticated لربط placeholder يجب أن تستخدم `auth.uid()` نفسه، وبريداً مؤكداً، وتطابقاً داخلياً وحيداً؛ وإلا ترفض (`42501`).
- الدالة `SECURITY DEFINER` ذات `search_path = pg_catalog, public, auth` ولا يملك `PUBLIC` أو `anon` أو `authenticated` أو `service_role` حق تنفيذها مباشرة.
- تحديث بريد الملف العادي لا يمس الرابط، وقد ثُبت ذلك محلياً.

## 15. حد الدعوات

الدعوة الحالية لا تنشئ دعوة Supabase Auth كاملة، وهذا لم يُعد تصميمه في B4. المستخدم المدعو الجديد يبقى `auth_user_id = NULL` حتى أول تسجيل دخول مؤكد يمر بالمحلل المركزي. تفحص خدمة الفريق البريد الداخلي وكذلك البريد الحالي لهويات Auth المرتبطة، وترفض `IDENTITY_INVITATION_CONFLICT` عند تعدد المرشحين. العضوية تظل `active` وفق السلوك القديم، لكنها لا تمنح جلسة بلا Auth UUID مرتبط؛ تغيير lifecycle الدعوة مؤجل بموافقة مستقلة.

## 16. أثر RLS

التغيير الوحيد هو جسم `current_workspace_ids()`: أزيل join البريد مع `auth.users` واستبدل بـ`public.users.auth_user_id = auth.uid()`. لم تتغير السياسات الثلاثون أو الأدوار أو FORCE RLS. اجتازت الدالة فحوص المالك الموثوق، و`SECURITY DEFINER`، و`search_path`، وعدم `PUBLIC EXECUTE`. اجتازت عزلة A/B وanon وservice-role guardrails.

## 17. التسجيل الأمني

استُخدم logger المنظم الموجود لتسجيل `LEGACY_LINKED` و`NEW_IDENTITY_PROVISIONED` ورفض التعارض/الالتباس. لا توجد بنية audit دائمة عامة مناسبة حالياً؛ `crm_activities` ليست سجل أمان. السجلات تعرض أول ثمانية أحرف فقط من UUID ولا تسجل بريداً أو token أو JWT أو كلمة مرور.

## 18. التهيئة الجديدة

أعيد ضبط Supabase المحلي ثم شغّل harness التهيئة السلسلة `0000 → 0001 → 0002 → 0003 → 0004`. النتيجة: خمس هجرات وخمس snapshots ولا ملفات SQL خارج journal، و30 جدولاً و189 قيداً و10 دوال عامة مصنفة و7 triggers. تطابقت البصمة المرصودة والمتوقعة، والقرار `ADOPTABLE`.

## 19. ترقية قاعدة موجودة

أنشأ اختبار rollback حالة catalog قبل B4، وزرع exact/no-match/ambiguous ثم طبق SQL الكامل لـ0004. رُبط exact وحده، وبقيت الحالات الثلاث الأخرى بلا رابط، ولم تتغير بياناتها. اختبر preflight مستقلاً الحالات الخمس: `1 exact / 1 no-match / 2 ambiguous rows / 1 already-linked / 1 conflict`. تعيد حالة conflict بوابة غير آمنة ولا تُحل آلياً. إعادة تشغيل migrator بعد التطبيق نجحت بلا إعادة تنفيذ للهجرة.

## 21. النتائج الأمنية

لا تبقى ثغرة HIGH/CRITICAL معروفة تسمح بتكرار الهوية أو Workspace بعد تغيير البريد. الربط UUID-first، والفريد والـtrigger والقفل الذري يمنعون الاستبدال والتكرار والسباق، وRLS لم يعد يعتمد البريد.

حدث انحراف إجرائي أثناء التحقق: استُدعي `db:migrate` مرة واحدة من دون override صريح، فقرأ `.env` وحاول الاتصال بعنوان pooler مستضاف. فشل الاتصال برسالة tenant/DNS قبل العبارة رقم 1؛ لذلك لم تُنفذ SQL ولم يتغير schema أو data أو ledger مستضاف. كل أوامر قاعدة البيانات اللاحقة استخدمت صراحة `127.0.0.1:54322`. بسبب شرط «عدم الوصول» المطلق لا يمكن تأكيد عدم حدوث محاولة الاتصال، ولذلك بوابة التسليم `REVIEW_REQUIRED` رغم اكتمال القبول التقني.

## B4.1 Hosted Connection Guard Review

يبقى سجل الحادث الأصلي أعلاه جزءاً دائماً من دليل B4: أثناء التنفيذ الأصلي حدثت محاولة اتصال واحدة بوجهة Supabase pooler مستضافة مأخوذة من `.env`. فشلت المحاولة قبل العبارة SQL رقم 1، ولم يتغير schema أو data أو migration ledger مستضاف.

حدد B4.1 السبب الجذري بدقة: كان أمر `npm run db:migrate` يشغّل `drizzle-kit migrate` مباشرة؛ يستورد `drizzle.config.ts` بيئة الإنتاج، ويحمّل `dotenv` قيمة `DATABASE_URL` من `.env`. لم يمر هذا المسار عبر حدود B1 التي تفرض `TEST_DATABASE_URL`، ولذلك كان ممكناً إنشاء عميل Drizzle قبل تصنيف الوجهة.

أغلق B4.1 هذا المسار كما يلي:
