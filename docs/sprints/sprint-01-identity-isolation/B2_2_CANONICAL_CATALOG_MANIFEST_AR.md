# B2.2 — بيان الكتالوج المرجعي وبصمة المخطط

## 1. الغرض

يوثّق هذا العمل الحالة المرجعية المقصودة لقاعدة بيانات Verix **قبل Sprint 1** بصيغة آلية وحتمية. وهو يطبّق قرار **Hybrid Canonical Adoption Point**: تبقى الهجرات التاريخية `0000`–`0016` محفوظة، ويُستخدم البيان لاحقاً للتحقق من قاعدة قائمة أو من نتيجة bootstrap مرجعي قبل السماح بالتبنّي. هذا العمل يصف الهدف فقط؛ لا ينشئ SQL إصلاحياً ولا يغيّر سجل الهجرات.

## 2. المصادر المرجعية

تمت مصالحة الأدلة التالية:

- تعريفات Drizzle في `src/server/db/schema/{tables,enums,columns,relations,index}.ts`.
- الهجرات التاريخية `drizzle/0000`–`0016` وبيانات `drizzle/meta` بوصفها أدلة، لا كسجل قابل لإعادة البناء.
- وظائف وسياسات ومنح RLS في `src/server/db/rls.sql` والتعديلات اللاحقة في `0014`–`0016`.
- افتراضات الخدمات والـ validators والاختبارات ووثائق قاعدة البيانات وSupabase.
- نتائج B1 وB2 وتصميم B2.1 المعتمد.

يأخذ مولّد البيان بنية الجداول والـ enums والفهارس من مخطط Drizzle الحالي، ويضيف الأجسام التي لا يعبّر عنها Drizzle بالكامل من SQL التاريخي، خصوصاً RLS والسياسات والمنح والوظائف والمشغلات وقيد منع تداخل الحجوزات.

## 3. تصنيف الملكية

- `verix_owned`: جداول `public` التطبيقية وأعمدتها وقيودها وفهارسها، ووظائف Verix وسياساتها ومنحها ومشغلاتها.
- `supabase_managed`: مخطط `auth` و`auth.users` و`auth.uid()` والأدوار `anon` و`authenticated` و`service_role` وقدرات المنصة التي لا يملكها Verix.
- `verix_required_extension`: امتداد متاح من البيئة لكن Verix مسؤول عن ضمان تفعيله لأن قيداً تطبيقياً يعتمد عليه.
- `legacy_only`: أجسام ظهرت في التاريخ ثم أزيلت ويجب ألا تكون موجودة في الحالة الحالية، وعددها ستة.
- `uncertain`: كل تعارض أو قرار ملكية/أمن لم يحسمه المستودع. وجود أي عنصر من هذا النوع يمنع قرار `ADOPTABLE`.

## 4. مخطط البيان

الملف `canonical-pre-sprint-1.json` يحمل `manifestVersion: 1` و`scope: pre-sprint-1`، ثم قوائم مستقرة لـ:

- الجداول والأعمدة: المخطط، الاسم، النوع المنطقي، nullability، default، identity وgenerated.
- الـ enums وقيمها المرتبة.
- القيود: PK وFK وUNIQUE وCHECK وEXCLUSION وخصائص الإرجاء والتحقق.
- الفهارس الصريحة فقط، باستثناء الفهارس الآلية التابعة للقيود.
- وظائف Verix وتوقيعاتها ونوع الإرجاع واللغة و`SECURITY DEFINER` وتصنيف ثقة المالك و`search_path` والجسم المطبّع.
- المشغلات وتوقيتها وأحداثها والدالة والتعريف.
- حالة RLS وFORCE RLS، والسياسات والأدوار و`USING` و`WITH CHECK`.
- المنح المحددة على أجسام Verix للأدوار التطبيقية المعتمدة.
- الالتباسات والأجسام التاريخية المتوقّع غيابها.

المتطلبات التي تملكها Supabase موجودة في ملف مستقل ولا تدخل في قوائم Verix.

## 5. قواعد البصمة

البصمة هي SHA-256 للنص JSON الحتمي الناتج من تطبيع وترتيب القوائم التالية فقط: `tables`, `enums`, `indexes`, `constraints`, `functions`, `triggers`, `rls`, `policies`, و`grants` مع `manifestVersion` و`scope`.

تطبّع الأداة المسافات وحالة الكلمات غير المقتبسة والاقتباس غير الضروري، وترتّب الأجسام بمفاتيحها المنطقية. تُرتب الأعمدة لأن ترتيبها الفيزيائي لا يغير عقد الكتالوج المقارن، بينما يبقى ترتيب قيم enum دلالياً. وتُعرّف المفاتيح الخارجية بأعمدة المصدر لا بالاسم الفيزيائي الذي اختلف بين Drizzle وSQL التاريخي. لا تدخل OIDs أو timestamps أو row counts أو IDs تشغيلية أو أسرار أو مالكو البيئة أو metadata متقلبة. كما لا تدخل `ambiguities` أو `legacyObjects` أو متطلبات Supabase في hash؛ لكنها تدخل قرار التبنّي بصورة مستقلة. البصمة الحالية:

`b84dd485f280a6fca69350787ea6bf9f658d4a84c247803c05bf51d6a5c09ee3`

## 6. فاحص PostgreSQL

`postgres-catalog-inspector.ts` ينفّذ استعلامات `SELECT` ثابتة فقط على `pg_catalog` و`information_schema`. يجمع جداول `public` وأعمدتها، enums، القيود، الفهارس غير التابعة للقيود، وظائف Verix وثقة مالكها، المشغلات، RLS، السياسات والمنح الفعلية ذات الصلة، بما فيها ACL الافتراضي للدوال، ثم يعيد نفس بنية البيان المطبّعة.

الأداة لا تنفّذ DDL/DML ولا تحدّث جدول الهجرات. مشغّل `test:db:catalog` يمر أولاً عبر حارس B1 الخاص بقاعدة الاختبار المؤقتة، ويطبع JSON آمناً يتضمن البصمتين والفروق والقرار. لا يعني اتصال PostgreSQL عادي اجتياز بوابة Supabase النهائية.

## 7. نموذج متطلبات Supabase

`supabase-prerequisites.json` يعلن ثمانية متطلبات `assert_only`:

1. الدور `anon`.
2. المخطط `auth`.
3. الدالة `auth.uid()` التي تعيد UUID.
4. العلاقة `auth.users`، ولا يطلب منها Verix إلا العمودين `id` و`email`.
5. الدور `authenticated`.
6. الامتداد `btree_gist`، المصنف بعد B2.3 كـ`verix_required_extension` مع `create_if_absent` لقيد عدم تداخل الحجوزات.
7. الدالة `pg_catalog.gen_random_uuid()`.
8. الدور `service_role` بحدود RLS المرتفعة الموثقة.

لا يبصم البيان البنية الداخلية الكاملة لـ Supabase ولا يحاول إعادة إنشائها.

## 8. تصنيفات الفروق

محرك المقارنة يستخدم هذه الفئات فقط:

- `exact_match`: الجسم المنطقي متطابق بعد التطبيع.
- `compatible_drift`: فرق محدود في فهرس غير فريد قد يكون آمناً، لكنه يحتاج allowlist وموافقة صريحة. لا يستطيع الـ allowlist تخفيض فرق أمني أو قيد أو جدول أو enum إلى هذه الفئة.
- `missing_required_object`: جسم مرجعي مطلوب غير موجود.
- `unexpected_object`: جسم Verix ذو صلة موجود وليس في المرجع.
- `unsafe_conflict`: الاسم المنطقي نفسه موجود بتعريف قد يغيّر الصحة أو الأمن أو القيود أو RLS أو سلوك البيانات.

المقارنة تقريرية فقط ولا تصلح أي جسم.

## 9. بوابة التبنّي

- `ADOPTABLE`: جميع الأجسام المطلوبة متطابقة، ولا drift غير محسوم ولا التباس.
- `NOT_ADOPTABLE`: يوجد جسم مطلوب مفقود أو تعارض غير آمن.
- `REVIEW_REQUIRED`: يوجد compatible drift أو جسم غير متوقع أو دليل مستودع مصنف `uncertain`.

الأولوية لـ `NOT_ADOPTABLE` إذا اجتمعت أكثر من حالة. حسم B2.3R الالتباسات الثلاثة، لكن يبقى تطبيق SQL الذي ينتج هذا الهدف مسؤولية B2.4.

## 11. الالتباسات المحسومة

حسم B2.3R على Supabase المحلي الرسمي:

1. تطبيع casts والأقواس والـpartial indexes والـexclusion constraint مع إبقاء grouping الدلالي.
2. تصنيف مالك `SECURITY DEFINER` إلى trusted/untrusted/unknown من دون إدخال اسم الدور الحرفي في البصمة.
3. تمثيل effective ACL واشتراط غياب `PUBLIC EXECUTE` عن وظائف Verix.

قائمة `ambiguities` الحالية فارغة.

## 12. الأجسام الحساسة أمنياً

الأكثر حساسية هي وظائف `SECURITY DEFINER` الثلاث الخاصة بسياق workspace، سياسات RLS الثلاثون، حالة RLS لكل جدول، منح الجداول والدوال، وظائف billing immutability ومشغلاتها، مفاتيح workspace الخارجية، وقيد عدم تداخل الحجوزات. أي اختلاف في الجسم أو search path أو التعبير أو الدور أو الأمر أو FORCE RLS يصنّف تعارضاً غير آمن لا compatible drift.

لا تحفظ الأدوات عناوين اتصال أو كلمات مرور أو مفاتيح Supabase، ولا تطبعها.

## 13. الاختبارات

تغطي اختبارات B2.2:

- تطابق artifact المخزن مع إعادة توليده والبصمة الجانبية.
- الترتيب الحتمي واستقرار البصمة عند اختلاف ترتيب القوائم.
- تغير البصمة عند تغير قيمة enum.
- استبعاد metadata المتقلبة ومتطلبات Supabase من بصمة Verix.
- غياب بيانات الاعتماد من البيان.
- FK مختلف، policy مفقودة، وتعبير RLS مختلف.
- جدول غير متوقع وcompatible drift.
- القرارات الثلاثة `ADOPTABLE` و`NOT_ADOPTABLE` و`REVIEW_REQUIRED`.

هذه اختبارات pure ولا تحتاج قاعدة حية. فحص PostgreSQL متاح اختيارياً فقط عبر بيئة B1 الآمنة.

## 14. استخدام B2.3 للبيان

B2.3R شغّل المتطلبات والـobserved manifest على Supabase محلي، وحقق 493 exact matches بلا drift أو conflict. يستخدم B2.4 البيان نفسه كهدف اختباري عند تصميم consolidation/adoption من دون تعديل التاريخ أو تلفيق ledger.

## 15. القيود المعروفة

- التطبيع parser محافظ لتراكيب boolean المدعومة، وليس parser PostgreSQL عاماً؛ كل تركيب جديد يحتاج regression evidence.
- الفاحص يحصر النطاق في `public` وأجسام Verix ذات الصلة، وليس كتالوج cluster كاملاً.
- اسم مالك الدالة الحرفي مستبعد، لكن تصنيف الثقة portable يدخل البصمة.
- metadata الخاصة بالامتداد ليست ضمن بصمة Verix؛ availability عقد prerequisite منفصل.
- البيان مشتق من الأدلة الحالية؛ أي تغيير مشروع لاحق للمخطط يحتاج تحديثاً صريحاً للبيان وإعادة توليد البصمة.

## 16. معايير القبول

- يوجد بيان JSON ثابت للحالة قبل Sprint 1 وملف بصمة SHA-256 منفصل.
- كل جسم مصنف ضمن حدود الملكية المعتمدة، والالتباس مسجل لا مخفي.
- متطلبات Supabase مستقلة ولا تدّعي Verix ملكيتها.
- يوجد فاحص PostgreSQL read-only ومحرك فرق وبوابة تبنٍّ بلا auto-repair أو metadata writes.
- تغطي الاختبارات الحتمية والفئات والقرارات والمخاطر المطلوبة.
- لا توجد تغييرات في الهجرات أو journal أو snapshots أو RLS أو مخطط التطبيق.
- لا يوجد consolidation migration ولا وصول إلى production.
